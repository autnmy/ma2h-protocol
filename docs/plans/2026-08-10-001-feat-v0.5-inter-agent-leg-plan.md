## Key Technical Decisions

### KTD1 — UQ1: the three entry signed contexts (the decision this issue owns)

All three follow the house pattern: detached signature, RFC 8785 JCS canonical serialization,
`MA2H-Signature: t=..,jti=..,v1=..` wire header, digest-over-fixed-key-wrapper, per-delivery fresh
`t`/`jti` (mailbox-rest rule, §9.7), keys listed in JCS (lexicographic) order. Normative home: new
**§9.8** ("Inter-agent entry integrity").

1. **`message` entry** — same key set as §9.7's `inbound_signed_context` (deliberate reuse):

   `message_signed_context = { "from", "id", "jti", "ma2h_version", "payload_sha256", "t", "to" }`

   `payload_sha256` = lowercase-hex SHA-256 of JCS(`{ "message": <content> }`) where `<content>`
   carries exactly the delivered envelope's **present** fields among `type`, `title`, `body`,
   `priority`, `tags`, `context`, `request`, `action`. Rationale: `type` is bound (flipping
   notify/ask/task materially changes recipient behavior; §9.7 had a single type so didn't need
   this); `request`/`action` are bound because an ask's request block enters the recipient's LLM
   context exactly as instructions do (SCP r2 finding 12). `created_at`/`expires_at` stay
   Hub-authoritative advisory (unbound — mirrors §9.7); the `agent` descriptor stays advisory
   (mirrors §9.2's unbound top-level `agent`); attested identity is the bound `from`.
2. **`response` entry** — §9.2's `signed_context` with `callback_url` replaced by `to` (the
   session-qualified destination address), everything else identical **including** the §9.2
   `payload_sha256` over JCS(`{ "response": <response|null>, "state": <state|null> }`):

   `response_signed_context = { "id", "in_reply_to", "jti", "ma2h_version", "payload_sha256",
   "resolution", "resolution_id", "resolved_at", "t", "to" }`

   Rationale: maximal reuse — a verifier shares the §9.2 digest code path; `to` supplies the same
   cross-destination replay defense `callback_url` supplies on push. The §6 Response body stays
   byte-for-byte (MINOR discipline), so `to` lives **only in the signed context**, reconstructed by
   the drainer from its own presented identity (`agent:<own id>#<presented session>`) exactly as
   §9.2 verifiers reconstruct `callback_url` from their own endpoint.
3. **`receipt` entry** — mirrors §14.4's ack pattern (dedicated digest, fixed-key wrapper, absent
   optionals as `null`):

   `receipt_signed_context = { "in_reply_to", "jti", "ma2h_version", "receipt_sha256", "t", "to" }`

   `receipt_sha256` = lowercase-hex SHA-256 of JCS of the fixed-key object
   `{ "at", "event", "in_reply_to", "prior", "session" }` (all five keys always present; an absent
   member serializes as `null`, exactly as §14.4's `ack_sha256` wrapper). The receipt **envelope**
   is `{ ma2h_version, type: "receipt", in_reply_to, event, prior, at, session, to }` — the SCP's
   field list (`in_reply_to`, `event`, `prior`, `at`, terminal session id) plus envelope plumbing
   (`ma2h_version`, `type` for discrimination, `to` for the uniform addressee check + destination
   binding). The plumbing addition is noted on the SCP thread as part of the UQ1 resolution comment
   (composition, not deviation — the SCP's lists never enumerate `ma2h_version` either).

### KTD2 — Delivered `message` entry form (what the digest covers is what the addressee gets)

The Hub delivers the submitted §4 envelope with Hub-assigned `id` and Hub-attested `from`
(`agent:<id>` or `agent:<id>#<sess>`), and MUST strip submitter-side machinery: `state` (submitter's
opaque resume blob, §9.3; round-tripped only in the Response), `client_ref` (§9.1 already forbids
exposing it to resolvers — the addressee is the resolver), and `request.callback`/`action.callback`
(the submitter's delivery config; leaking its URL/auth shape to the addressee serves nothing).
`idempotency_key` is retained (inert to the addressee; keeps the delivered form validating against
the ask/task branches of `message.schema.json`, which require it). The v0.5 `inbound-message` schema
**forbids** `state`/`client_ref`/nested `callback` on the delivered branch — the §13.4-analog
strip-unsigned-fields defense (they are outside `payload_sha256`, so an on-path injector could add
them without breaking the signature).

### KTD3 — `to` grammar as a schema pattern

`^agent:[^#]+(#sess_.+)?$` — first `#` terminates the agent-id segment; the session segment must
match `^sess_`. A `#`-bearing agent id is inexpressible in `to` (its own `#` splits early and the
remainder fails `^sess_`), which the spec states as the S2 consequence; S1 already bans such ids
from registering sessions. `agent.session` gets `^sess_.+$`.

### KTD4 — Version-aware conformance routing, not a fork of the harness

`reference/src/envelope.ts` gains a second ajv registry compiled from `schema/v0.5/` (9 files) and a
v0.5 validator lookup by schema filename; `reference/src/conformance.ts` routes any vector whose
`target` starts with `v0.5/` to that lookup. The v0.4 switch and every existing vector are
untouched, so v0.4 stays green by construction. New v0.5 vectors are named `sv-017+` with
`"target": "v0.5/<file>"`.

### KTD5 — One new top-level section only (§16), everything else amends in place

Following the SCP's own amendment map (S2 "amends §4, §5, §7, §8.1"; S3 "amends §5, §6, §8.7, §13";
…) and issue #25's scope line. The entry-kind shapes and drain semantics live in §8.7; the signed
contexts in new subsection §9.8; sessions in new §16. §1 gains terminology (Session; and an explicit
disambiguation of the §14 "acknowledgment (receipt)" vs the v0.5 `receipt` **entry kind** — the SCP
reuses the word deliberately, the spec must keep them distinct). §3.1 durability is extended to
cover active session leases and un-acked mailbox entries of every kind (a restart-forgotten lease
would be an undocumented third terminal path; follows from S1's two-terminal state machine).

### KTD6 — Deterministic worked-example values computed with the reference JCS

The worked signature examples use the house test key (`ma2h-test-secret-key-0123456789ab`) and
values computed by a throwaway script against `reference/src/canonicalize.ts` + node crypto — same
provenance as `directive-signature-v0.4.md`. The doc states that the corresponding `dp-*`
conformance fixtures land with #27.

### U1. `schema/v0.5/` snapshot

**Goal:** The nine v0.5 schemas, valid Draft 2020-12, `$id`s under `https://ma2h.org/schema/v0.5/`.
**Requirements:** R2, R4 (error codes are spec-table-only; no schema), KTD2, KTD3.
**Dependencies:** none.
**Files:** `schema/v0.5/message.schema.json`, `schema/v0.5/response.schema.json`,
`schema/v0.5/submit-ack.schema.json`, `schema/v0.5/get-message.schema.json`,

`schema/v0.5/ack.schema.json`, `schema/v0.5/presence.schema.json`, `schema/v0.5/session.schema.json`.
**Approach:** Copy v0.4, re-`$id` all files + intra-schema `$ref`s (`inbound-message` and
`get-message` cross-reference sibling schemas by absolute `$id`) to the v0.5 path; titles "(v0.5)".
Then: `message` adds optional `to` (KTD3 pattern) and `agent.session`; `capability` adds `sessions`
(`enabled` required; `max_ttl_seconds`, `max_live_per_agent`, `agent_list_visibility` boolean,
`terminal_retention_seconds` — S1 says the terminal-readability window is advertised),
`inter_agent` (`enabled` required + description "default false, account-opt-in";
`entry_kinds` array of enum `message|response|receipt`; `sender_allowlists` boolean with
REQUIRED-support description), `inbound` additions (`stream_url` uri, `stream_max_hold_seconds`
int, `session_param` boolean); `submit-ack` status enum gains `queued` and adds optional
`destination` object (`state` enum `online|offline|unknown` required, `last_seen` optional,
closed) — parent stays `additionalProperties:false` with `destination` listed (the SCP's named
schema change); `inbound-message` becomes a `oneOf` of four delivered payload branches: directive
(v0.4 branch verbatim, version pattern `>=0.4`), delivered inter-agent message
(allOf-`$ref` v0.5 message + required `id`/`from`/`to`, `from` pattern per KTD3, version `>=0.5`,
forbids `state`/`client_ref`/nested `callback` per KTD2), response entry (`$ref` v0.5 response),
receipt (new `$def`: required `ma2h_version` `>=0.5`, `type` const `receipt`, `in_reply_to`,
`event` enum `["bounced"]`, `prior` enum `["queued","delivered"]`, `at` date-time, `session`
`^sess_`, `to` session-qualified pattern); `session.schema.json` new: root = the session resource
(required `id` `^sess_`, `agent_id`, `state` enum `active|closed|expired`, `created_at`,
`expires_at`; optional `ttl_seconds`, `label`, `kind`, `project`, `labels`, `run_id`, `closed_at`)
plus `$defs` for the register request (all fields optional) and register/read/list response
wrappers.
**Patterns to follow:** v0.4 schema conventions (descriptions carry spec § refs; version-floor
patterns like `^0\.([4-9]|[1-9]\d+)$`).
**Test scenarios:** covered by U3's vectors (each new constraint gets a positive and a negative
vector; see U3).
**Verification:** ajv compiles all nine without errors (exercised by U2's registry + U3's vectors
through `npm test`).
